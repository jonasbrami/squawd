Product design brief · single-drone rebuild · 2026-07

A drone that sees for itself —
and only asks the LLM to think.

One drone. One pilot agent. A YOLO instance-segmentation model and a single-point laser rangefinder do the seeing — the LLM only orchestrates, in text, on a Kimi subscription with Claude as fallback. No VLM vision on any tier: perception is 100% local. A 10 Hz classical controller does the flying. Every claim below is gated by a geometric oracle and survived two independent high-effort design reviews with full codebase and web access.

01

The problem we are solving

why rebuild

The LLM was the whole perception loop

Every pixel that informed a decision went through Claude vision — image tokens and seconds of latency per look. Meanwhile the one place vision should feed — the pursuit controller's contact source — was wired to simulator ground truth, and only inside evals. Interactively, track had no contact feed at all.

The swarm came before the single drone

Commander, fleet ops, N-way port plumbing — surface area without the thing that matters: a single drone that perceives well, flies well, and is measurable. The rebuild drops the swarm and makes one drone excellent.

02

Design principles

non-negotiable
1

LLM plans, classical executes

The pattern that unlocked moving-target missions. The LLM sets what; tight loops handle how. Now extended from control to sensing.

2

Idle costs nothing

Poll-based wakes, seq-keyed frame/inference dedupe, no per-tick LLM calls. An idle drone spends zero tokens.

3

Ground truth is for grading

The known map stays in the flight path; live object truth never touches it — it exists to score the system.

4

Tool results are verifiable

Gap/dwell numbers, structured health, stable result codes — the LLM can check its work against its task.

5

One authoritative perception

What flies the drone is exactly what the UI overlays and what evals measure. No divergent copies.

03

The system in one view

information & decision flow

Decisions flow down the center; measurements flow up the right. Ground truth exists only to grade — never to fly.

05

Sensing: camera first, laser for the chosen one

the perception stack

The camera says what and which way; the rangefinder says exactly how far — for one designated target, inside an honest envelope.

Every visible object — the camera

  • YOLO11n-seg (nano, ONNX Runtime, CPU) per new frame — box + instance mask
  • Footpoint + attitude at the frame's stamp → bearing (full pinhole intrinsics)
  • Ground movers: support-plane geometric range (~1–3 m at 20–40 m alt)
  • CV-EKF per track: source covariances, innovation gating, bearing-only dropout mode

The one designated target — the laser

  • LW20/TF03-class single-point ToF (~100 m class, 0.3–0.5° beam, ~$220–300)
  • Fuses only inside the envelope: shadow · ≤3 m/s · near co-altitude · beam on target
  • Beam footprint ⊂ one mask (or 20–25 % eroded box) + range-consistency gate
  • Everywhere else: opportunistic — used when valid, never depended on
Reliable fusion

shadow · slow · co-altitude · beam locked — <0.5 m p50, ≥80 % availability

Opportunistic

intercept & chase speeds — fused only when every gate passes; the chase never depends on it

Bearing-only

no range — EKF keeps the track (COASTING); acquisition works to win the lock

From first sight to locked pursuit

DETECTEDbearing-only contact in frame
DESIGNATEDtrack(id) accepted without a range
ACQUIRINGyaw + level onto it, bounded beam-lock retries
RANGE_LOCKEDlaser associated — metric distance, any altitude
TRACKEDEKF world track feeds the 10 Hz pursuit
COAST→LOSTdropouts degrade gracefully, never fly away
Why the envelope is honest: a multicopter pitches 10–25° at chase speed — pitch is the speed actuator — and a body-fixed ~1–2° beam cannot stay on a sub-meter target through that. Nobody ships body-fixed 1D target ranging. The first draft of this design said "TF-Luna, any altitude, precise" — the dual web review killed all three claims (8 m sensor · pointing physics · masks we didn't have). This is the corrected design: gimbal and mmWave radar are the named future upgrades.

The build plan

8 gated milestones

Branch rebuild-single-drone from feat/dynamic-scenarios. Every milestone ships only when its gate passes.

Testing strategy — few, sharp, contract-bound: every test maps to a contract (one test per promise; anything that can't fail is deleted). Three defense lines: per-module contract tests with shared fakes (sim-free), ONE architecture gate (AST import scan of the dependency matrix), and reality gates (one sim smoke per milestone + the oracle harness). 41 tests + 3 spike scripts for the entire rebuild — including the regression tests born from the reviews (pipeline starvation, consumption order, envelope rejections).

M0 — Kimi spike ½ day

Sim-free: auth + real endpoint via debug logs, multi-turn MCP on a dummy server, tier vars.

GATE ▸ backend proven before any rebuild effort

M1 — Single-drone skeleton + ops hardening

Pilot agent + 12 tools at M1 (13 once detect lands at M2) + estop + non-latching commands. Doctor-preflight gate, fail-closed startup, central safety envelope, stable result codes, unit-test fakes. Delete commander/fleet (+test migration).

GATE ▸ pytest green · doctor FAIL = no launch · estop <2 s · envelope rejects out-of-range, no motion

M2 — Frames, projection, detector, laser reader

Atomic Frame + pose/attitude interpolation + full-intrinsics projection. Detector (blob → ONNX; +UltralyticsBackend — visdrone aerial classes from day one) + dormant tracker registry (BoT-SORT/CSRT/SAM2 extras). Composite x500_depth_range: 3×3 ray-bundle + impairment shim.

GATE ▸ p50 contact error <5 m @ ≤30 m (ground mover, 12 m/s transit) · shim rejects dropouts · raw snapshots on /pilot/detections

M2.5 — Training pipeline

Auto-labeled, domain-randomized Gazebo renders → nano instance-seg ONNX (+SHA-256 manifest).

GATE ▸ beats blob backend · adds obstacle class · ≤25 ms/frame CPU

M3a — Vision-fed track, core

VisionContacts (EKF, health, stable IDs) + O1–O5: contact duck-type, LOST semantics, velocity dispatch, contact-aware face/goto, heading-wait. Ground truth demoted to grading.

GATE ▸ d2_shadow 2/2 camera-fed AND 2/2 truth-fed · structured LOST on dropout

M3b — Laser fusion the envelope

Acquisition state machine + envelope-gated fusion + mask/eroded-box association + consistency gate.

GATE ▸ <0.5 m p50 / <1.5 m p95 slant · ≥80 % availability · 0 false associations · airborne acquisition

M4 — Cockpit observatory parallel view mock

Cockpit POV tile: POV video + full sensor-fusion HUD (boxes + ids + range-src chips, ToF beam indicator, track-state banner, attitude ladder, sensor health, degraded banners) + PPI map + chat + estop button.

GATE ▸ overlay tracks the mover · SEARCHING → LOCKED visible · stale overlays dropped · estop holds mid-track

M5 — Evals + perception grading

Truth/flight deps split, per-cell reset, TargetLockEvent → oracle, decoy tasks, ID-switch metrics, strategy-snippet A/B, primitive statistics.

GATE ▸ suite green at N=1 · accuracy report · pilot/null-pilot dual gates

M6 — Kimi in-sim switch

Env recipe → launcher + evals tiers (uniform text-only tool path; no VLM vision anywhere by design).

GATE ▸ spike checks + mini-ladder on kimi tier with quota metrics

Learning from siblings

AerialClaw investigation

Two independent code-level investigations of AerialClaw (MIT, closest sibling: LLM agent + PX4/Gazebo + skills). Conclusion: borrow operational patterns, not subsystems — net code intake ≈ zero lines.

✓ Adopted — 7 patterns

  • Health-gated startup — doctor preflight with hard deadlines M1
  • Fail-closed / no-silent-mock — prove px4+connected or refuse M1
  • Central enforced envelope — in code, no YAML M1
  • Stable result codes — NOT_READY…ESTOPPED M1
  • Narrow protocol fakes — unit tests only M1
  • Versioned strategy snippets — activated on measured lift M5
  • Oracle-derived statistics — observational only M5

✕ Rejected — with code evidence

  • Memory / reflection / vector stores — mostly dead code; harms eval reproducibility
  • Approval gate — does not exist in their code; our estop covers override
  • WASD manual — unarbitrated second PX4 writer (v1 keeps estop)
  • 5 cameras — 97 % of their frames go unused; 5× detector load
  • 2D LiDAR — sensor SDF not even in their repo
  • Universal device protocol — fleet plumbing, unauthenticated actions
  • Safety YAML — loaded by zero lines of Python
  • Identity docs (SOUL/BODY) — half-generated, half-stale, self-contradicting
Free validation: their live loop is 50+ serial cloud-LLM round-trips per task with LLM-guessed distances and a mock detector — direct evidence for our two core refusals: no LLM inside the fast loop, no cloud VLM in the perception loop.
